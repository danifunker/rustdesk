# Mac OS X 10.6: what to try, and what to look for

**Status: untested. Nothing is knowingly in the way, and nothing has been run.**

This exists so the next attempt starts from what is already established rather
than re-deriving it. Everything below marked *measured* was; everything marked
*expected* was not.

---

## The two scenarios, which are different problems

**A. PowerPC hardware running a 10.6 that supports it.** Snow Leopard shipped
Intel-only, so whatever this is, it is not something whose behaviour can be
looked up. The agent's APIs are the question, not the CPU.

**B. An Intel Mac on 10.6 with Rosetta.** The CPU is the question, not the APIs.
Rosetta is an optional install on 10.6 rather than a default one, and it is gone
entirely from 10.7 — so this scenario has a hard ceiling at 10.6.

They can fail independently and for unrelated reasons. Test whichever you have
and record which one it was; a result from one says almost nothing about the
other.

---

## Already settled, so do not redo it

* **The build targets the G4** (`-mcpu=7450`, `cpusubtype` 10 / `ppc7400`).
  This is deliberate and load-bearing for scenario B: Apple's published Rosetta
  limitations include applications that require a G5, so a `ppc970` binary would
  not run under it at all. See [`BUILD.md`](BUILD.md).
* **Nothing the agent calls was removed in 10.6.** `CGDisplayBaseAddress`,
  `CGDisplayBytesPerRow`, `CGDisplayBitsPerPixel` and `CGPostMouseEvent` were
  *deprecated* in 10.6, not withdrawn. Upstream's capture uses `CGDisplayStream`,
  which is 10.8+; this agent does not, and the only mention of it in the tree is
  a comment saying why.
* **`LSMinimumSystemVersion` is 10.4.0** and no maximum is set anywhere, so the
  bundle will not refuse to launch on a newer system.
* **The G4 build serves a full session on a G5** — measured, so a failure on
  10.6 is about 10.6 and not about the G4 targeting: 16 frames, 2 keyframes,
  first frame 0.87 s, a 1920x1080 screenshot in 0.75 s, and the C colour shim
  byte-identical to the Rust reference.

## What to expect to break, in order

Each of these degrades rather than crashes, and each says something specific in
`~/rustdesk-ppc-agent/agent.log`. That is the point of reading the log rather
than watching the screen.

### 1. The framebuffer read — most likely

`CGDisplayBaseAddress` is exactly the API Apple deprecated in 10.6 for no longer
being meaningful, and under scenario B it is being asked for a pointer into an
Intel machine's framebuffer. Expect it to return NULL or something unusable.

```text
capture unavailable: display 1 reads 0x0, 0 bpp, stride 0, base 0x0;
                     first tried Ns ago, last succeeded Ns ago
video unavailable: ... -- retrying every 5s
```

**This is survivable and the agent is built for it**: the session still serves
input and clipboard, and rebuilds the video pipeline every five seconds
(`VIDEO_RETRY`) in case it comes back. Two numbers in that line matter — how
long the process had been running, and whether capture had *ever* worked in it.
"Worked and then stopped" and "never worked" have different causes.

If this is what happens, the fix is a different capture path, and the honest
options are poor: `CGDisplayStream` is 10.8+, and the older
`CGDisplayCreateImage` is 10.6+ — which would work on 10.6 and nowhere earlier,
so it would have to be selected at runtime.

### 2. The cursor shape

`CGSCurrentCursorSeed` and `CGSGetGlobalCursorData` are private CGS calls, and
private calls are exactly the ones that move between releases.

```text
cursor: falling back to the built-in arrow
```

Already handled: an unreadable shape falls back to the built-in arrow rather
than to no pointer. Cosmetic.

### 3. AltiVec under Rosetta (scenario B only)

libvpx carries 53,648 hand-written AltiVec instructions and the agent links
42,117 of them; our own code emits none (measured — see `BACKLOG.md` §13).
Rosetta is documented as translating G3 and G4 code, but whether its AltiVec
translation is complete enough for libvpx's kernels is **not something that can
be established from here**. If frames arrive corrupted rather than not at all,
this is the first suspect.

### 4. The clipboard

The Pasteboard Manager is unchanged in 10.6, so this should simply work — but it
needs the Aqua session, which is a launch question rather than an OS one. If
`clipboard unavailable` appears, that is the LaunchAgent not being loaded with
`-S Aqua`, not 10.6.

## How to run the test

```bash
# On the 10.6 machine, from the disk image:
#   drag the app to /Applications, launch it, press Install.
# Or headless:
sh "/Applications/Agent for RustDesk PPC.app/Contents/Resources/install.sh" --yes
```

`install.sh` warns rather than refuses on an unexpected OS version — it accepts
10.4 and 10.5 silently and says "continuing anyway" for anything else, which is
what makes this test possible without a code change.

Then, in order:

1. **Does the app launch?** It is a Cocoa binary built for the G4. Under Rosetta
   this is the first thing that could fail, and it fails visibly.
2. **What does the status block say?** ID, "Built for", and whether the service
   is running. Screenshot it.
3. **Does the service start?** `Install` then `Start`, or
   `~/rustdesk-ctl status`.
4. **Connect a real client** by IP first (simplest path, no server involved),
   then by ID if a rendezvous server is configured.
5. **Read the log** — `~/rustdesk-ppc-agent/agent.log`, or the app's *Show Log*
   button. This is the actual result; what the screen does is a summary of it.

## What to bring back

```bash
sw_vers                                    # which 10.6, and the build
machine ; sysctl -n hw.optional.altivec    # CPU, and whether AltiVec is claimed
uname -a
file ~/rustdesk-ppc-agent/rustdesk-agent   # confirm which slice/arch is installed
tail -100 ~/rustdesk-ppc-agent/agent.log
```

The log matters more than a description of the symptom: "no picture" covers a
dead framebuffer, a failed encoder and a session that never started, and those
three lines above tell them apart.

## If it works

Two things change, and both are small:

* `install.sh` should stop saying "continuing anyway" for 10.6;
* `LSMinimumSystemVersion` stays at 10.4.0, but `BUILD.md` and the README should
  say 10.4–10.6 rather than 10.4/10.5.

Neither is worth doing speculatively.
